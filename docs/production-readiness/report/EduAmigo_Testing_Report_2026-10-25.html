EduAmigo: testing report

What was tested, at how many users, what went wrong, and what was changed. Local testing on one MacBook, 25 October 2026.

In one paragraph. EduAmigo was tested with simulated users from 10 up to 1,000 at the same time, and every screen of every role was opened and used. The system stayed up and never showed one school's data to another. Errors were essentially zero: 4 requests out of about 124,000 failed in one Stage F run, and none failed in any other run. Testing found one performance problem (signing in was slow when about 1,000 people signed in within a minute, up to 4 seconds), which is now fixed (about 60 milliseconds), and four real product bugs, also fixed. Not yet tested: 2,500, 5,000 and 10,000 users, and several heavy features. Nothing here proves EduAmigo can carry 10,000 users.

The one real performance problem: signing in at 1,000 users

At 1,000 users all signing in within about a minute (roughly 17 sign-ins per second), signing in took about 4 seconds, and ordinary pages also slowed to 3 seconds during that minute. Nothing failed, but it would feel broken.

Cause (measured, not guessed): passwords were checked by a library written in plain JavaScript that runs on the same single thread that answers every request. Each check takes about 50 ms, so 17 per second used most of that thread and everything else waited. The machine overall was only 11 to 17 % busy and the database was fine, so the limit was that one thread, not the hardware or MongoDB.

Fix: use the native version of the same password library, which does the checking on separate worker threads. Existing passwords keep working, nobody has to reset anything, and password strength was not reduced.

3. Problems in the tests themselves (found and corrected, so the numbers can be trusted)

  • A false pass. The first Stage A run reported success, but the first 10 simulated users were all students, so parent, teacher and office traffic was never sent. The assignment was changed to spread roles evenly and the run was repeated.
  • A false alarm. Stage B flagged "one cross-school response". Investigation showed the server answered 200 with an empty list and zero totals when asked for another school's student: no data from another school was exposed. The test now counts a response as a leak only when it contains records, and logs what it received. (It would be tidier for the server to answer 404 there.)
  • Two functional checks were found to always report success, regardless of what happened. They were replaced with real checks before the results below were recorded.

5. What was changed

In the product

  • Sign-in now uses the native bcrypt password library (new file src/services/passwordHash.js, used by the user model and the password service). If it cannot load on some server, it automatically falls back to the old library, with one warning in the log.
  • Sign-in concurrency limit: at most 3 password checks at the same time, up to 300 waiting. Beyond that a sign-in gets a clear "Sign-in is very busy, try again in a few seconds" message (503), never "wrong password". Reason: in a measurement, 250 sign-ins at once made an unrelated file read wait 3.4 seconds; with the limit it waited under 1 millisecond. Cost: a pure sign-in flood is served about 30 % slower. Settings: PASSWORD_CHECK_CONCURRENCY and PASSWORD_CHECK_QUEUE.
  • One new dependency: bcrypt (version 6) and two small helpers. Ready-made binaries are included for macOS, Linux and Windows.
  • Frontend: the four fixes in section 2.

Not changed, on purpose

  • No password was reset or re-hashed, the password strength setting (cost 10) was not lowered, who may sign in did not change, and the sign-in and password-reset rate limits are as before. No extra server instances were added.

In the testing tools (backend loadtests/)

  • A one-command staged runner for Stages A to I. It uses a throw-away database on this Mac, never touches any real database, blanks every external-service key (no real email, SMS, payment or AI calls), and stops by itself on sustained server errors, any cross-school data, low memory, or if the app or database stops. Stages above 1,000 users need an explicit flag; Stage I also needs Stage H to have passed.
  • Realistic user journeys for the four roles, after-run data checks, a cross-school check, a record of the test records created (with a separate, opt-in cleanup command), and an event-loop delay probe.

6. What is still unknown or unproven

  • Not run: 2,500, 5,000 and 10,000 users. The load generator (k6) used about 3.4 to 5 GB of memory at 1,000 users, so 5,000 or more cannot be generated reliably from this Mac; a separate machine is needed.
  • Not in the load test yet: fee payments, chat with attachments, concerns, profile-photo upload, the school bus GPS updates and live map, reports, year-end, and the AI features. Bus updates are likely the heaviest write load in real use.
  • The database in these tests is in memory on the same Mac. A real hosted database over a network, with real data volumes, will behave differently. These figures show where the application itself becomes slow, not what production will do.
  • Only one application instance was tested. The sign-in ceiling for one instance is now roughly 60 sign-ins per second; beyond that, more instances are the answer.
  • One 361 ms pause was seen once in one run after the fix (120 ms in the other); its cause was not found.
  • Browsers other than Chrome, and real phones, have not been tested.
  • Live-test data on the local demo: the tests added notices, homework, attendance, a part-payment, chat messages and a bus trip to the local demo school only. Nothing was changed in any real school.
  • Nothing has been committed, pushed or deployed. All changes are in the working folders.

7. Suggested next steps

  1. Add fee, chat and bus-update journeys to the load test and re-run Stages B to F.
  2. Run Stage G (2,500 users) after closing other apps; this needs an explicit go-ahead.
  3. Rent a separate load-generator machine for 5,000 and 10,000 users, and point it at a test copy of the real hosting setup (same server size and database tier), not at production.
  4. Before any of that goes live, review and commit the changes in groups.
